# scikit-learn docs RAG assistant

Локальный помощник по основам Classic ML. Отвечает на вопросы на русском и английском по документации scikit-learn, показывает источники ответа и выводит текст постепенно в Gradio. Доступны REST API на FastAPI и интерфейс в браузере.

Корпус строится из десяти выбранных страниц документации scikit-learn 1.9 (`linear_model`, `tree`, `model_evaluation`, `ensemble`, `cross_validation`, `preprocessing`, `compose`, `grid_search`, `impute`, `feature_selection`) и локального `data/local/about.md`. `app/scripts/load_corpus.py` сохраняет чанки с URL разделов и стабильными ID в `data/corpus_chunks.jsonl`; `app/scripts/index_corpus.py` загружает их в Qdrant. При запросе dense и BM25 находят кандидатов, Qdrant объединяет их через RRF; опциональный reranker переставляет кандидатов перед выбором четырёх лучших чанков. Сервис передаёт эти чанки LLM и показывает тот же список источников пользователю.

## Подготовка

Нужны Python 3.11 или новее, Docker с Compose для Qdrant, доступ к интернету для загрузки документации и модели эмбеддингов, а также ключ OpenAI-совместимого LLM-провайдера. По умолчанию настроены Groq, модель `qwen/qwen3.8-27b` и локальный эмбеддер `intfloat/multilingual-e5-small`.

В корне проекта создайте **не коммитируемый** файл `.env`:

```dotenv
LLM_API_KEY=your_provider_key
```

При другом провайдере задайте в нём `LLM_BASE_URL` и `LLM_MODEL`. Не публикуйте действующий ключ.

## Запуск через Anaconda Prompt

Команды выполняются из корня репозитория. Если окружение `sklearn-rag` уже создано, пропустите первую команду.

```bat
conda create -n sklearn-rag python=3.11 -y
conda activate sklearn-rag
python -m pip install -r requirements.txt
docker compose up -d qdrant
python -m app.scripts.load_corpus
python -m app.scripts.index_corpus
python -m uvicorn app.main:app --reload
```

`load_corpus` скачивает десять страниц scikit-learn 1.9, выделяет основные разделы, сохраняет код и создаёт локальный JSONL. `index_corpus` создаёт коллекцию `sklearn_docs_<хеш корпуса>_hybrid_<хеш параметров>`, проверяет схему, оба вектора каждой точки, UUID, тексты, metadata и пробный dense/hybrid-поиск, затем переключает alias `sklearn_docs`. Повторный запуск с тем же JSONL и параметрами проверяет уже активную коллекцию без перезаписи точек. Для E5 документы кодируются с `passage: `, запросы — с `query: `; сам текст чанков остаётся без префикса. Если Qdrant ещё запускается, дождитесь его готовности и повторите команду индексации.

### Переход с dense-индекса этапа 2

Сохраните существующий `data/corpus_chunks.jsonl`: повторно скачивать документацию для перехода не нужно. Остановите приложение, выполните `python -m app.scripts.index_corpus` и запустите его снова. Новая коллекция содержит именованные векторы `dense` и `bm25` в каждой точке; прежняя коллекция и каталог Qdrant сохраняются. До переиндексации `/ready` возвращает `503`, поскольку старый индекс несовместим с новой схемой.

По умолчанию `RETRIEVAL_MODE=hybrid_rerank`: до 20 dense-кандидатов и до 20 BM25-кандидатов объединяются серверным RRF, затем reranker оценивает до 40 уникальных чанков и выбирает четыре. Повторы устраняются по UUID чанка, а разные чанки одного раздела сохраняются. Допустимы также `dense` и `hybrid` без reranker; задайте нужный `RETRIEVAL_MODE` в `.env` и перезапустите приложение.

BM25 выполняется непосредственно локальным Qdrant 1.19.1, без FastEmbed и внешнего inference-сервиса. Индексация и запросы используют одинаковые параметры: word-токенизация, lowercase, английские stopwords, без stemming и ASCII folding; `k=1.2`, `b=0.75`, `avg_len=256`, серверный IDF. BM25 помогает находить имена API в английском корпусе, а E5 обеспечивает семантический поиск для русских вопросов. Изменение модели E5, нормализации или BM25-параметров меняет имя физической коллекции и требует переиндексации.

### Поиск с reranker

Для отдельной проверки reranker в Anaconda Prompt выполните:

```bat
conda activate sklearn-rag
set RETRIEVAL_MODE=hybrid_rerank
python -m uvicorn app.main:app --reload
```

В этом режиме `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` оценивает пары «исходный вопрос — текст чанка» для всех объединённых кандидатов. После сортировки по score в LLM и источники передаются до четырёх лучших; при одинаковом score сохраняется порядок RRF. Модель работает на CPU, длина пары ограничена 512 токенами, batch size — 8. Полный текст выбранного чанка передаётся в LLM: ограничение длины применяется только при оценке пары моделью.

Модель загружается при первой успешной инициализации RAG, обычно при старте приложения, и переиспользуется в течение жизни процесса, включая восстановление связи с Qdrant. При первом запуске нужен интернет для скачивания весов; последующие запуски используют кэш Hugging Face. `--reload` создаёт новый процесс при изменении файлов, поэтому в нём модель загружается заново. При ошибке загрузки `/ready` возвращает `503`; при ошибке inference запрос завершается существующей ошибкой поиска. Автоматического переключения на другой режим нет.

Имя модели можно задать через `RERANKER_MODEL`; после смены нужен перезапуск приложения. Переиндексация для смены reranker не требуется. В режимах `dense` и `hybrid` reranker не загружается. MiniLM выбран по сравнительному прогону ниже.

## Запуск целиком в Docker

Создайте `.env`, как описано выше, затем из корня репозитория выполните:

```bat
docker compose build app
docker compose up -d qdrant
docker compose run --rm app sh -c "python -m app.scripts.load_corpus && python -m app.scripts.index_corpus"
docker compose up -d app
```

Загрузка корпуса и индексация идут в одном временном контейнере: созданный там JSONL исчезнет после команды, а индекс останется в локальном `qdrant_data_v2/`. Старый `qdrant_data/` сохраняется отдельно. Для повторной индексации повторите команду `docker compose run`: новая коллекция станет активной только после проверки. Оба каталога Qdrant и `.env` не коммитьте.

## Проверка

- Gradio: <http://127.0.0.1:8000/> — ответ поступает по частям, источники отображаются рядом.
- API-документация: <http://127.0.0.1:8000/docs>.
- `GET /health` — процесс работает; не проверяет индекс.
- `GET /ready` — `200`, если активная коллекция доступна, её схема и параметры совместимы с приложением и RAG инициализирован; иначе `503`. После появления совместимой коллекции сервис может восстановиться без перезапуска.
- `POST /chat` — JSON `{"question": "What is Ridge regression?"}`; ответ содержит `answer` и `sources` (`url`, `snippet`).

Пример запроса из Anaconda Prompt:

```bat
curl.exe -X POST http://127.0.0.1:8000/chat -H "Content-Type: application/json" -d "{\"question\":\"What is Ridge regression?\"}"
```

Автоматические проверки без обращения к настоящим Qdrant и LLM:

```bat
python -m pytest -v
```

## База оценки поиска

Набор `data/eval/retrieval_questions_v1.json` содержит 30 вручную размеченных вопросов: 24 по корпусу (12 EN, 12 RU, все десять тем, точные имена API), включая четыре вопроса из двух частей, и 6 вне корпуса. Каждый URL в `expected_urls` — обязательный раздел с якорем. У вопросов из двух частей требуются два разных раздела; у вопросов вне корпуса список пуст.

После локальной загрузки корпуса и индексации выполните из Anaconda Prompt:

```bat
python -m app.scripts.eval_retrieval
```

Сценарий использует только dense-вектор новой коллекции, независимо от `RETRIEVAL_MODE`, локальный E5 и Qdrant, без вызовов LLM или RAGAS. Он проверяет, что активный alias соответствует локальному JSONL и параметрам индекса, и выполняет весь прогон по найденной физической коллекции, даже если alias затем переключится. Результат сохраняется в `notebooks/retrieval_dense_v2.json`: хеш корпуса, физическая коллекция, модель, упорядоченные top-4 URL со score, метрики каждого вопроса и сводка по языкам и категориям. При повторном запуске этот отчёт перезаписывается после успешного завершения всех запросов. Исходная dense-база этапа 2 в `notebooks/retrieval_baseline_v1.json` сохраняется для сравнения. Старые оценки в `notebooks/rag_metrics.json` относятся к прежнему корпусу.

- **Recall@4** для вопроса — доля обязательных разделов, найденных в четырёх чанках. Повторы одного раздела не увеличивают Recall; сводка усредняет значения по вопросам.
- **MRR@4** — обратный ранг первого чанка из любого обязательного раздела; при отсутствии попаданий — 0. Ранги исходной выдачи сохраняются, включая повторы.
- **Полное покрытие** вопросов из двух частей — доля вопросов, у которых найдены оба обязательных раздела.
- **Вне корпуса:** dense-поиск возвращает кандидатов даже без нужного материала. Их выдача записывается отдельно, а Recall/MRR для них не считаются.

База для `intfloat/multilingual-e5-small`, коллекции `sklearn_docs_e52561b2d50a` (704 чанка):

| Поднабор | Вопросов | Recall@4 | MRR@4 |
|---|---:|---:|---:|
| Все покрытые | 24 | 0.8542 | 0.8021 |
| EN | 12 | 0.9583 | 0.8542 |
| RU | 12 | 0.7500 | 0.7500 |
| Один раздел | 20 | 0.9000 | 0.7875 |
| Две части | 4 | 0.6250 | 0.8750 |

Полное покрытие двух частей — **1/4 (25%)**. Это результат на небольшом фиксированном наборе: русские и составные вопросы показывают текущие ограничения dense-поиска. Для сравнения следующих вариантов поиска нужно сохранить тот же набор вопросов и проверить совпадение хеша корпуса в отчётах.

## Сравнение поиска: этап 3

Из того же локального корпуса (704 чанка) и на тех же 30 вопросах выполнены свежие dense, hybrid и hybrid + MiniLM прогоны по **одной физической гибридной коллекции**. Шесть вопросов вне корпуса не входят в Recall/MRR. Сценарий сверяет хеш корпуса с базой этапа 2, фиксирует физическую коллекцию, проверяет UUID, текст и URL каждого найденного чанка и не вызывает LLM:

```bat
conda activate sklearn-rag
python -m app.scripts.compare_retrieval
```

Отчёт `notebooks/retrieval_comparison_v1.json` содержит параметры и версии моделей, UUID/URL/score в порядке выдачи, метрики по каждому вопросу, языку и категории, изменения поимённо и три прогона задержки. Исходный отчёт этапа 2 `notebooks/retrieval_baseline_v1.json` сохранён без изменений.

| Режим | Recall@4, 24 | MRR@4, 24 | RU Recall / MRR, 12 | Две части: полное покрытие | p50 / p95 поиска | Пик памяти процесса |
|---|---:|---:|---:|---:|---:|---:|
| Dense | 0.8542 | 0.8021 | 0.7500 / 0.7500 | 1/4 | 33.6 / 55.7 мс | 1372 МиБ |
| Hybrid (RRF) | 0.9167 | 0.8438 | 0.8750 / 0.7917 | 2/4 | 35.5 / 55.6 мс | 1372 МиБ |
| Hybrid + MiniLM | **0.9375** | **0.9028** | **0.9167 / 0.9444** | 1/4 | 2891.6 / 3719.2 мс | 2084 МиБ |

По сравнению с dense MiniLM улучшил Recall на `ru-02`, `ru-08` и MRR на `en-03`, `ru-01`, `ru-02`, `ru-08`. Ухудшился MRR на `en-04`, `en-06`, `ru-11`; потерь Recall нет. По сравнению с hybrid MiniLM улучшил Recall на `ru-08`, но ухудшил его на `ru-11`; MRR вырос на `en-03`, `ru-02`, `ru-08`, `ru-10` и снизился на `en-04`, `en-06`, `en-07`, `ru-11`. У составных вопросов MiniLM снизил полное покрытие с 2/4 до 1/4. Эти ухудшения видны в отчёте по вопросам, а итоговая приёмка сравнивает выбранный режим со свежим dense на том же индексе. Общие и RU Recall/MRR MiniLM выше обоих вариантов, поэтому условие запуска BGE не наступило.

Замер: Windows 11, Intel Family 6 Model 154 (20 логических CPU), Python 3.12.14 и CPU PyTorch 2.14.0; Qdrant 1.19.1 запущен локально. Каждый режим запускался в отдельном процессе: загрузка E5 и MiniLM измерена отдельно, затем два прогревочных запроса и три последовательных прохода по 30 вопросам. p50/p95 посчитаны по 90 полным поисковым запросам без времени загрузки моделей. Пиковая память — максимум RSS/working set процесса поиска по счётчику ОС с учётом загрузки моделей, без памяти Qdrant. Загрузка E5 заняла 10.9–14.6 с, MiniLM — 8.3 с (веса уже были в кэше). Порядок UUID в hybrid менялся между проходами, хотя сводные метрики совпали; упорядоченные UUID, URL и score в отчёте относятся к первому проходу. На этой машине MiniLM добавляет около трёх секунд к поиску без учёта генерации ответа.

## Выбор эмбеддера: этап 4

По результатам эксперимента 30 сентября 2026 года оставлен **`intfloat/multilingual-e5-small` (384)**. `intfloat/multilingual-e5-large` (1024) сравнивался на том же корпусе из 704 чанков и тех же 30 вопросах, с одинаковыми BM25, RRF, MiniLM, E5-префиксами, нормализацией и top-4. Шесть вопросов вне корпуса исключены из Recall/MRR.

| Эмбеддер | Recall@4, 24 | MRR@4, 24 | RU Recall / MRR, 12 | Две части: полное покрытие | p50 / p95 поиска | Пик памяти сервиса |
|---|---:|---:|---:|---:|---:|---:|
| E5 small | 0.9375 | 0.9028 | 0.9167 / 0.9444 | 1/4 | 1629.0 / 2236.5 мс | 2087 МиБ |
| E5 large | 0.9375 | 0.9028 | 0.9167 / 0.9444 | 1/4 | 1878.5 / 2917.8 мс | 3978 МиБ |

Условия перехода на large проверяются одновременно:

- **Не выполнено:** абсолютный прирост MRR@4 минимум на 0.05; фактический прирост — **0.00**.
- **Выполнено:** Recall@4 не снизился.
- **Выполнено:** p95 не выше удвоенного small; фактическое отношение — **1.30**.
- **Выполнено:** пиковая память сервиса строго ниже 6 000 000 000 байт; у large — **4 171 264 000 байт**.

На каждом покрытом вопросе Recall/MRR совпали: побед и ухудшений по этим метрикам нет, в том числе на RU и составных вопросах. Порядок UUID между моделями изменился у 9 из 30 вопросов, но порядок выдачи каждой модели и сводные метрики стабильны во всех трёх проходах. Large на этом наборе не дала требуемого прироста качества, увеличив p95 примерно на 30% и почти удвоив пиковую память. Это результат небольшого фиксированного набора, а не вывод о превосходстве small на любых данных; качество генерируемых ответов здесь не оценивалось.

### Повтор эксперимента через Anaconda Prompt

Нужны запущенный Qdrant, исходный локальный `data/corpus_chunks.jsonl` и активный small-индекс, соответствующие базе этапа 2. Настройки `EMBEDDING_MODEL` / `EMBEDDING_DIM` должны оставаться `intfloat/multilingual-e5-small` / `384`. Повторно скачивать корпус для эксперимента не нужно.

```bat
conda activate sklearn-rag
python -m app.scripts.compare_embeddings
```

Сценарий строит отдельную физическую коллекцию large через `index_corpus --no-activate --device cpu`, проверяет обе коллекции и сохраняет рабочий alias `sklearn_docs` на small. Уже существующая экспериментальная коллекция проверяется без перезаписи; неполная или несовместимая коллекция вызывает ошибку. Для large при первом запуске нужны интернет и место для весов в кэше Hugging Face. При успешном повторе отчёт заменяется; при сбое предыдущий завершённый отчёт сохраняется. Чтобы записать новый результат отдельно:

```bat
python -m app.scripts.compare_embeddings --output notebooks/embedding_comparison_repeat.json
```

Полный отчёт: [notebooks/embedding_comparison_v1.json](notebooks/embedding_comparison_v1.json). В нём сохранены хеши корпуса и вопросов, физические коллекции, параметры и версии моделей, упорядоченные UUID/URL/score, метрики по вопросам и категориям, все проходы и проверка каждого критерия. Рабочая small-коллекция — `sklearn_docs_e52561b2d50a_hybrid_b497cf557f46`, экспериментальная large — `sklearn_docs_e52561b2d50a_hybrid_bd1e64f1782a`. Обе содержат 704 точки; small остаётся моделью по умолчанию, переиндексация для применения решения не требуется.

Замер выполнен на Windows 11, Intel Family 6 Model 154 (20 логических CPU), Python 3.12.14, PyTorch 2.14.0+cpu (14 потоков), sentence-transformers 6.0.1 и Qdrant 1.19.1. Small и large запускались последовательно в отдельных процессах настоящего FastAPI/Gradio-приложения через lifespan; генерация заменена локальной заглушкой, вызовов LLM не было. После двух прогревочных запросов выполнены три прохода по 30 вопросам для каждой модели. p50/p95 рассчитаны по 90 запросам от кодирования вопроса до финального reranking, без загрузки моделей и генерации; таблица качества относится к первому проходу.

Память — пик RSS/working set всего процесса сервиса по счётчику ОС, включая импорт приложения, FastAPI/Gradio, TestClient, E5, MiniLM, запуск и измеренные запросы. Память Qdrant, отдельного процесса индексации и остальных процессов не включена. Задержки этапов 3 и 4 получены в отдельных прогонах; решение об эмбеддере основано на свежем сравнении small и large внутри этапа 4.

## Текущие ограничения

- Корпус охватывает десять выбранных тем; оценка поиска опирается на 24 покрытых вопроса. MiniLM улучшает общие и RU метрики, но увеличивает задержку и снижает полное покрытие двух составных вопросов по сравнению с hybrid.
- Загрузчик сохраняет основной текст статьи, блоки кода и URL с якорем раздела. После обновления JSONL необходимо повторно запустить `index_corpus`, чтобы новые темы появились в поиске.
- База оценки поиска содержит 30 вопросов; качество генерируемых ответов на новом корпусе пока не измерено.
- Имя физической коллекции зависит от корпуса и параметров индекса. Повторный запуск с теми же данными и параметрами сохраняет существующие векторы; прежние коллекции автоматически не удаляются.
- Qdrant server и client закреплены на 1.19.1. Если у вас уже запущен старый Qdrant, `docker compose up -d qdrant` переключит сервис на новый каталог `qdrant_data_v2/`; старый каталог останется на диске.
